# Distúrbio por interceptação — resumo do que mudou (2026-10-01, issue #73)

- Mecanismo final, no `monjolo`: `StateRegistry` ganhou `register_disturbance(keys, interceptor)` — registra um grupo de chaves que passa a ser interceptado por quem implementa o trait `DisturbanceInterceptor` (`active()`/`apply(raw)`).
- **A interceptação acontece no `offer::` (escrita), não no `need::` (leitura)** — decisão explícita do usuário, trocada de uma versão anterior read-side. `Proxy::set()` (escalar) e a nova `Proxy::set_group()` (grupos `Mixture`, ver abaixo) checam, a cada escrita, se há uma cadeia registrada pra aquela chave; se houver, o valor passa por ela ANTES de ser gravado no buffer. `need::`/`Proxy::get()` voltou a ser uma leitura pura, sem checagem nenhuma — o valor já guardado é sempre o final.
- **Cadeia, não um interceptador só**: `resolve()` agrupa todos os `register_disturbance` que compartilham o MESMO conjunto de chaves numa lista ordenada (ordem de registro) e anexa essa lista aos `Proxy` que OFERECEM aquelas chaves (`offered_proxies`, um mapa novo em `StateRegistry`, populado em `subscribe()`). Cada estágio da cadeia só roda se `active() != 0.0`; o resultado de um estágio vira o `raw` do próximo.
- **`resolve()` erra se a chave não tiver ofertante real** — um `#[disturbance]` nunca é o CRIADOR do valor que intercepta, só o modifica; registrar pra uma chave que ninguém publica é erro, igual qualquer `need::` sem provedor.
- **`Proxy::set_group(proxies, values)`**: nova função — grupos `Mixture` eram escritos como N `.set()` separados (um por componente), mas uma cadeia precisa ver o grupo INTEIRO do mesmo tick de uma vez (IDV(1)/IDV(2) mexem em A e B simultaneamente). `#[task]`'s `offer::nome::<Mixture>` agora gera uma chamada a `set_group`, não mais um loop de `.set()`.
- **Macro final (sem mudança desde a iteração anterior): `#[monjolo::disturbance(key, intercepts, [components, species])]`**, mesmo padrão de `#[actuator]`/`#[sensor]`/`#[controller]`: struct sem campos, getters (`self.active()`, `self.raw()`), `disturb(&self)` escrito à mão, sem parâmetro — só que agora `self.raw()` não lê mais nenhum `Proxy` próprio (não precisa mais `need::` as próprias chaves que intercepta): o valor chega como argumento de `apply()`, guardado temporariamente num `Cell`/`RefCell` interno só pra `self.raw()` enxergar.
- **`IDV(1)` e `IDV(2)` implementados e CONVIVEM**: `Idv1`/`Idv2` (`tep-plant/src/disturbance/`) interceptam a MESMA chave (`flows.stream4_composition`) — ligados os dois, os efeitos se SOMAM exatamente como o `teprob.f` original (`A = nominal - 0.03·IDV1 - 0.00243719·IDV2`, `B = nominal + 0.005·IDV2`), não um apagando o outro. Prova de ponta a ponta em `tests/disturbance/idv1_and_idv2.rs`.
- **Mudança de comportamento explícita**: antes, só quem `need::` via o valor interceptado (quem oferecia sempre via o cru). Agora só existe UM valor gravado por slot — quem oferece e quem pede enxergam o mesmo, já transformado. Intencional (decisão do usuário).
- `disturbance/mod.rs`: sem `Disturbances` compartilhado — cada IDV é um tipo próprio. `idv3.rs`..`idv20.rs` continuam CASCA (só comentário).
- `disturbance/mod.rs` também perdeu o `Disturbance` (singular) de canal cúbico/pulso — código morto desde a migração pro scheduler de dataflow (issue #10), apagado de vez.
- Commits: branch `73-mixture-chemistry` (monjolo) e `73-idv1-disturbance` (tep-plant).

## As três iterações, em ordem (e por que cada uma foi descartada)

1. **Função pura dentro de `#[monjolo::tasks]`**: `#[disturbance(key=..., intercepts=..., components=[...])]` sozinho num método, virando `fn(active: f64, raw: &[f64]) -> Vec<f64>` sem `&self`. Funcionava, mas o usuário pediu pra seguir a convenção de `#[actuator]`/`#[sensor]`/`#[controller]` (getters + método convencional, não parâmetro de função).
2. **Struct dedicada, interceptando no `need::`**: `#[monjolo::disturbance]` como macro própria, `disturb(&self)` sem parâmetro, lendo via `self.raw()` (um `Proxy` que o próprio struct subscrevia como `need::`). Resolvia a convenção, mas só suportava UM interceptador por chave — tentar implementar IDV(2) (que intercepta a MESMA chave que IDV(1)) quebrava o boot da planta inteira (`resolve()` errava por colisão), mesmo com os dois desligados.
3. **Struct dedicada, interceptando no `offer::`, em cadeia (final)**: o usuário propôs mover a interceptação pra escrita — resolve os dois problemas de uma vez (overhead de recomputar a cada leitura; e, principalmente, permite que vários distúrbios se encadeiem na mesma chave, exatamente como o `teprob.f` precisa). Exigiu a peça nova de `Proxy::set_group` pra grupos `Mixture` não perderem atomicidade.

## Tática/padrão de projeto usado

- **Interceptor/Decorator em CADEIA** — mais perto de um pipeline de verdade agora (tipo `.pipe()` do RxJS) do que a versão anterior deste documento descrevia: múltiplos estágios, cada um opcionalmente transformando o valor antes de repassar ao próximo, aplicados em ordem de registro. Zero estágios = passa reto; um ou mais = cada um decide, via `active()`, se participa.
- **A transformação em si é uma Strategy, carregada por `Rc<dyn DisturbanceInterceptor>`** — `Proxy`/`StateRegistry` não sabem nada sobre A/C ratio, IDV(1) ou qualquer química; só sabem "existe uma lista de algo com `active()`/`apply(raw)` pra aplicar, em ordem".
- **A "vacância" (`Option<Rc<Vec<...>>>`) existe em TODO `Proxy`, mas só é preenchida em quem precisa.** `None` é o estado inicial — a grande maioria do sistema nunca ganha uma cadeia e nunca paga custo nenhum por essa possibilidade existir.
- **Resolvido em tempo de INICIALIZAÇÃO (bootstrap), nunca em tempo de leitura OU escrita extra.** A cadeia é montada uma única vez, dentro de `StateRegistry::resolve()`, depois que TUDO já se registrou (`subscribe()`/`register_disturbance()`). O CUSTO de rodar a cadeia (se houver) acontece na escrita normal que `#[task]` já fazia de qualquer forma — não é um passo extra, é o mesmo `offer::` de sempre, só que potencialmente transformado no caminho.
- **`Proxy::set_group` existe porque grupos não são átomos de graça.** Um `Mixture` de N componentes sempre foi N slots `f64` independentes por trás — escrevê-los um a um é suficiente quando ninguém olha o grupo como um todo, mas uma cadeia de distúrbio PRECISA ver as N componentes do MESMO tick juntas (IDV(1) e IDV(2) mexem em componentes diferentes do mesmo grupo ao mesmo tempo). A macro de `#[task]` foi ajustada pra sempre escrever grupos `Mixture` atomicamente através desta função, nunca mais num loop de `.set()` solto.
